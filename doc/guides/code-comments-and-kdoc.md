# 代码注释与 KDoc

本专题是新增、修改、重构或审查源码时的必读规范，适用于自有 Kotlin、Java、C++ 及构建脚本中的维护性说明。

[返回编码规范主入口](../coding-guidelines.md)

## 1. 基本原则

- 使用规范中文说明意图、约束、风险、时序及非直观取舍，代码标识符、协议名和算法术语保留原名。
- 优先说明为什么、由谁负责、何时有效、失败后如何恢复，不逐行复述赋值与函数调用。
- 注释只描述当前事实；修改行为、异常、单位、顺序或生命周期时同步更新，不能把未实现的设想写成保证。
- 多项说明使用 `-` 无序列表，源码 KDoc、行内注释和 TODO 不使用数字分步；协议版本、业务数字及本文档章节编号不受此限制。
- 不写真实 Cookie、账号凭据、鉴权 URL、用户媒体信息或开发者机器路径。示例使用虚构数据及仓库相对路径。
- 通过命名或职责拆分就能表达的内容，优先改善代码；不为满足注释数量添加模板化句子。

## 2. 注释类型

| 类型 | 用途 |
| --- | --- |
| KDoc `/** ... */` | 说明类型职责、API 契约、边界、生命周期和异常 |
| 行内注释 `//` | 解释紧邻代码块的状态守卫、阶段、时序与非直观取舍 |
| TODO | 记录明确的后续动作、触发条件或可追踪问题 |

C++ 等语言采用对应文档注释方式，保持相同的契约要求。第三方源码保留其许可证和原有风格，不为语言统一批量改写上游注释。

## 3. 类型级 KDoc

必须覆盖：

- ViewModel、Repository、Manager、UseCase、Service 等核心业务类型。
- 公共接口、跨页面能力、公共工具和存储、网络、媒体、JNI 的边界类型。
- 维护任务注册、并发控制、状态机、事务协调或资源生命周期的内部类型。
- 含单位、稳定编码、特殊空值或权限含义的公开模型。

首句说明角色，再按需要解释职责、输入输出、所有权、线程和释放者。简单私有值对象可简化；类型名本身已表达的含义无需重复扩写。

以下注释示意服务任务登记类应说明的契约，不是新增类型要求：

```kotlin
/**
 * 记录当前下载服务实例负责的唯一任务，协调重复启动与安全退出。
 *
 * - 同一任务重复启动时不重复登记，但更新最近一次 startId。
 * - 最后一个任务结束时返回停止判断所需的 startId。
 * - 登记操作同步执行，页面不参与该集合的维护。
 */
```

## 4. 方法级 KDoc

公共及受保护 API、所有 `@UiIntentObserver` 方法和复杂内部方法须写明契约。私有方法若涉及状态变化、事务、文件发布、资源释放、权限或复杂算法，也不能仅靠可见性省略说明。

按真实需求包含：

- 首句说明操作目标。
- `@param` 描述业务身份、单位、合法范围与所有权，说明参数是否会被修改或清理。
- `@return` 描述结果、空值或特殊状态的含义。
- `@throws` 仅列实现确实可能抛出且调用方需要了解的异常。
- 补充线程、挂起、取消、幂等和重试契约；使用 `[Type]`、`[method]` 引用相关符号。

纯透传且没有额外约束的访问器可以简化。不要使用非标准标签代替自然语言契约，也不要保留失效参数名。

发布方法的文档应能让调用方看出何时可以清理源文件，例如：

```kotlin
/**
 * 将工作资源发布到公共媒体库，并持久化恢复检查点。
 *
 * 最终资源记录保存成功前保留源文件，避免发布或落库中断后失去有效副本。
 *
 * @param resource 待发布或恢复的资源记录。
 * @param forcePublish 是否继续已开始的发布流程，忽略当前内部存储设置。
 * @param persistCheckpoint 保存中间 URI 或最终资源记录的回调。
 * @return 可用于后续读取的最新资源记录。
 * @throws IOException 当资源不可用或内容写入、核验失败时抛出。
 */
```

实际 KDoc 必须跟随对应方法实现维护，不能直接复制示例承诺代码并未保证的行为。

## 5. 方法体阶段注释

方法体有效代码超过 15 行时，必须用紧邻代码块的行内注释划分关键阶段。有效代码不含函数签名、空行与纯注释行。只在方法开头写一句总括性描述不算阶段说明。

应特别解释：

- 操作身份、状态与权限校验为何要先完成。
- 任务去重、锁保护范围以及停止请求与迟到回调的竞争关系。
- 临时文件创建、网络或媒体执行、内容核验、检查点和最终记录提交。
- 删除、失败补偿、重试入口、取消传播及 `finally` 中的清理责任。
- 因平台兼容、性能或一致性要求而采用的非直观顺序。

例如，下面的续传分支应解释覆盖重下的原因：

```kotlin
// 服务端返回完整内容时不能追加旧缓存，否则续传文件会重复包含前半段。
if (resumeBytes > 0L && !append) {
    cacheFile.delete()
    resumeBytes = 0L
}
```

不使用“执行操作”“更新变量”“处理数据”等可套用到任意代码的说明。若长方法不能用少量阶段解释清楚，应先按职责拆分。

## 6. 本项目必须解释的领域约束

| 领域 | 注释应回答的问题 |
| --- | --- |
| 下载状态 | 持久化 TaskStatus 与执行器 DownloadStatus 如何区分，何时算整项任务完成 |
| 去重与服务退出 | 谁拥有任务集合，重复 startId 与最后任务退出如何协调 |
| 文件发布 | 哪一步保存 URI，何时可删除源文件，失败后的有效副本在哪里 |
| Room 迁移 | 哪些字段是稳定契约，默认值与历史关联如何保留 |
| Cookie 与权限 | 数据来源、必要使用范围、失效与取消语义，不写真实敏感值 |
| 播放与频谱 | Player、Listener、分析任务和 Bitmap 谁创建、共享与释放 |
| JNI / FFmpeg | 参数格式、单位、输入输出所有权以及错误后的清理责任 |

## 7. TODO、功能清理与审查

- TODO 包含动作和触发条件，例如“新增下载状态时同步补充活动状态策略测试”，避免只有“优化”“待处理”。
- 不保留整段注释掉的旧代码；提交历史由 Git 承载。
- 功能删除后清理专用注释、文案、文档和图示，不用“已移除”或“不再支持某旧功能”记录历史。
- 为仍在执行的迁移和兼容分支说明必要背景，不能将有效兼容约束与无用历史注释一起删除。

审查时检查类型与方法契约是否完整，阶段说明是否贴近代码，注释是否符合当前行为，是否存在数字分步、敏感数据、无意义复述或失效链接。
