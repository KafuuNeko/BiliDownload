# 代码美观与可读性

本专题是新增、修改、重构或审查源码时的必读规范，约定排版、命名、参数表达、控制流及 UI 代码的可读性要求，适用于自有源码与构建脚本。

[返回编码规范主入口](../coding-guidelines.md)

## 1. 排版与格式化

- Kotlin 使用[自动代码格式化](./code-formatting.md)调用 Android Studio 原生 `Reformat Code` 引擎，与编辑器共同读取本仓库的[项目代码样式](../../.idea/codeStyles/Project.xml)；[样式选择配置](../../.idea/codeStyles/codeStyleConfig.xml)已启用项目设置，Kotlin 使用官方预设。
- 缩进、折行、括号位置、尾逗号及声明间距以项目样式的格式化结果为准，不用大量空格手动对齐，也不为压缩行数将多个操作挤在一行。
- 新增或修改 `.kt` / `.kts` 后，依次执行 `formatApply`、同范围的 `formatCheck`，再由 AI 完成本专题的样式审计。导入清理由 `Optimize Imports` 或编辑完成，并核对没有通配符和未使用 import。
- XML、Java、C++ 等其他自有源码使用对应语言的项目样式完成排版，再由 AI 按本专题审查适用规则；自动化任务的文件范围是 `.kt` / `.kts`。
- 格式化范围限于任务相关代码，保留他人未提交的改动；不因历史排版差异扩大为全仓库格式化，第三方源码与生成文件保持其维护方式。
- 格式化工具负责排版，参数命名、条件分解、变量提取和控制流调整须结合类型、作用域及业务语义审查。

## 2. 命名与类型引用

- 名称说明对象的角色、操作和判断含义，遵循[命名速查](../coding-guidelines.md#6-命名速查)，避免含义不明的缩写；时长、字节、采样和索引应能看出单位或含义。
- 类型、构造函数及顶层函数通过显式 import 引入，在声明、参数、返回值、泛型和函数体内使用简短名称，避免反复内联完整包名。
- 名称冲突优先使用语义清晰的 `import ... as ...` 别名；确需全限定名时限制在消除歧义的最小范围。
- 提取局部变量或函数应表达业务概念、复用结果或降低理解成本，不为减少行数制造无意义封装；重命名时核对调用关系与 API 兼容性。

## 3. 参数与表达式

- 项目内业务 API、模型构造和多参数回调在语言支持时使用具名实参，例如 `foo(value = value)`；布尔值、数值、`null`、错误码及同类型参数尤其不能依靠位置猜测含义。
- 对照真实声明核对参数名、重载和默认值。Java 方法及函数类型的直接调用遵循语言限制，保留位置实参；具名 `vararg` 使用数组传值。标准集合构造和尾随 Lambda 沿用 Kotlin 惯用写法，避免为参数命名增加无意义包装。语法示例见 [Kotlin 具名实参](https://kotlinlang.org/docs/functions.html#named-arguments)。
- 包含多个业务判断的复杂条件按含义拆成解释性变量或职责明确的函数，避免重复否定、复杂嵌套和在同一表达式中混合校验与副作用。
- 条件拆分和变量提取须保留短路行为、求值次数与执行顺序，不能把依赖前置校验的访问或按需执行的调用提前求值。
- 字符串模板中避免嵌入复杂计算，先得到有意义的展示值；用户可见文案继续遵循[界面资源与主题](./ui-resources-and-theme.md)，通过字符串资源及占位符提供。

## 4. 控制流与作用域

- 优先使用提前返回、`continue` 等卫语句处理无效输入与边界情况，保持主要流程清晰；函数长度和嵌套深度遵循[主入口通用约束](../coding-guidelines.md#4-通用编码与改动约束)。
- Lambda 嵌套时使用有意义的参数名，避免多个隐式 `it` 或 `this` 让对象归属不明；需要时使用明确标签说明局部返回的目标。
- 集合操作、调用链和 `let`、`run`、`also`、`apply` 应清楚表达数据流；连续嵌套导致接收者、返回值或副作用难以识别时，改用局部变量或普通控制流。
- 简化代码时保持协程取消传播、线程切换、锁范围及资源清理责任，不能为缩短代码改变 `use`、`try/finally` 或事务的有效范围。

## 5. Compose 与 XML/DataBinding

- Compose 根据传入状态渲染并回传操作，复杂业务计算放在 ViewModel 或用例中；少量纯展示计算可使用名称明确的局部值，避免堆进组件参数。
- 多个回调或内容槽位容易混淆时使用具名参数，明确点击、确认、取消及内容渲染各自的用途，避免长串匿名 Lambda 隐藏事件含义。
- DataBinding 表达式保持简单，筛选、排序、资源选择和下载策略由业务层提供结果，避免在 XML 中堆叠三元判断与方法调用。
- 组件拆分围绕明确的视图职责与所需数据，不为减少单个函数行数创建只有转发作用的层级；页面与副作用规则见[页面实现与生命周期](./viewmodel-activity-compose.md)。

## 6. 审查与验证

- AI 样式审计在格式化与格式检查完成后执行，对照本专题逐项审查最终 diff；审计修改 Kotlin 代码后重新执行 `formatApply`、同范围的 `formatCheck` 和 AI 样式审计，直到最终改动通过。
- 审查名称、参数、条件和控制流是否清晰，逐项核对业务调用、模型构造和回调的具名实参，特别关注重载、嵌套作用域中的接收者、隐式参数及返回目标。
- 对照 diff 核对任务范围、求值顺序、空值处理、异常与取消语义，确认排版和可读性调整保持预期业务行为。
- 注释与 KDoc 遵循[代码注释与 KDoc](./code-comments-and-kdoc.md)，解释意图、边界和必要约束；可通过命名或拆分表达的内容先改善代码。
- 按[验证与交付](./testing-and-delivery.md)选择相应编译、已有测试或设备验证；格式和补丁检查不能替代业务验证，交付说明分别记录格式化、格式检查、AI 样式审计及业务验证的实际结果与限制。
